## 5. العيوب وخطوات إعادة الإنتاج

### QA-B01 — High — FK المعلن لا يمنع مالكًا غير موجود في MySQL المحلي

المكوّن المتأثر: سلامة البيانات الفعلية في `smart_day_planner_newtech.tasks`، وليس استنتاجًا بأن SQL المصدر بلا FK. الملف `server/db/migrations/002-tasks.sql` وSHOW CREATE TABLE كلاهما يحتويان `tasks_user_fk` نحو users وON DELETE RESTRICT، والمحرك InnoDB. السبب الجذري **غير محسوم**؛ لا ينسب هذا التقرير الخلل إلى Express أو إلى إصدار MySQL دون تحقيق إضافي.

إعادة الإنتاج التي نُفذت بالفعل على بيانات QA فقط:

1. قراءة `SELECT @@foreign_key_checks` أعادت 1، وقراءة COUNT للمستخدم 4294967295 أعادت 0.
2. محاولة INSERT مباشرة بعنوان `Invalid owner QA` و`user_id=4294967295` وتاريخ2044-02-29، والمتوقع رفض FK.
3. قُبل السجل305، وأكد LEFT JOIN أنه يتيم. فشل API-20 برسالة `Missing expected rejection.`؛ لم يُحوّل إلىPASS.
4. تحقق مستقل من أن المستخدم4000000000 غير موجود، ثم INSERT تشخيصي بعنوان `Phase6A FK diagnostic`.
5. قُبل السجل309 أيضًا؛ أظهرت القراءة النهائية سجلين يتيمين وchecks=1. كلاهما باقٍ، ولم يُحذف أو يُصحح.

الأثر: لا يمكن اعتماد ادعاء أن FK يضمن اتساق task→user على قاعدة التشغيل الحالية. لم يثبت تجاوز ملكية عبر HTTP: API يرفض `user_id` ويستمد المستخدم من الجلسة، واختبارات العزل نجحت. هذا يحد من مسار الاستغلال لكنه لا يعالج خلل سلامة DB.

المطلوب قبل التسليم: تحقيق مصرح به في بيئة MySQL وتعريف/تفعيل FK الفعلي؛ تحديد السبب ثم اعتماد الإصلاح وإعادة اختبار رفض المالك غير الموجود. التعامل مع السجلين التشخيصيين يحتاج موافقة حذف/تصحيح منفصلة؛ لا يُطلب أو يُنفذ تنظيف تلقائي في هذه المرحلة.

### QA-B02 — Low — ضياع تركيز لوحة المفاتيح بعد إلغاء حوار الحذف

المكوّن: `client/src/tasks/DeleteTaskDialog.jsx` واستخدامه من Daily Planner. ظهر مرتين مع مهمتين مختلفتين.

1. افتح Daily Planner ليوم فيه مهمة واضغط زر Delete الخاص بها.
2. يظهر dialog، والتركيز على Keep task كما هو متوقع.
3. اضغط Escape. يُغلق الحوار وتبقى المهمة.
4. `document.activeElement.tagName` يصبح `BODY`؛ المتوقع عودة التركيز لزر Delete الذي فتح الحوار.

الأثر: مستخدم لوحة المفاتيح يفقد موضعه ويحتاج التنقل من بداية الصفحة. لا حذف أو فقد بيانات. المطلوب لاحقًا إعادة التركيز إلى العنصر الذي فتح الحوار بعد الإلغاء، مع اختبار Escape وKeep task. لم يُعدّل المصدر.

لا عيب Critical مرصود، ولا عيب Medium مثبت في هذه الجولة. حدود التغطية والمخاطر أدناه لا تُسمى اختبارات ناجحة.

## 6. الأمان وسلامة البيانات

نجح سلوك الجلسات وhashing وrotation وlogout و401 وOrigin، والتعامل مع مدخلات SQL كمعاملات أو نصوص حرفية، وعزل المستخدمين وتزامن الطلبات. تم تدقيق الاستعلامات المعلّمة بالمعاملات في users وtasks، وقائمة الحقول المسموحة. DATE/TIME يعيدان نصًا في API، ولم يظهر انزياح تاريخ في الواجهة. اختبارات النموذج أثبتت Gregorian leap centuries ومناطق زمنية موجبة وسالبة دون تغيير المنطقة الزمنية للنظام.

الحفظ وعدم التكرار ناجحان للمهام المملوكة وواجهة العرض؛ **سلامة العلاقات العامة FAIL بسبب QA-B01**. نجح CHECK الوقت وفهرس in_progress الفريد. لا ادعاء بأن كل قيود قاعدة البيانات ناجحة.

خطة الحفاظ: بصمات SHA-256 محلية للسجلات الأصلية في users/tasks وتعريفات الجداول قبل الفحص وبعده؛ تطابقت جميعها. استُثني AUTO_INCREMENT من hash التعريف لأنه يتقدم طبيعيًا بعمليات QA، ولم تُقارن جلسات مستخدم حية قد تتجدد أو تنتهي تلقائيًا. لم تُفتح أو تُعدّل مستودعات الجامعة أو MADAR.

## 7. جاهزية التسليم الأكاديمي والمخاطر

الواجهة الإنجليزية واضحة وبنطاق تخرج صغير: التسجيل والدخول وإدارة المهام والأولوية والحالات والتواريخ والأوقات وDaily Planner وCalendar وDashboard مكتملة كوظائف مرصودة، عدا الحذف الدائم الذي لم يُعد اختباره في هذه المرحلة. استطاع حساب جديد تشغيل التدفق دون إعداد بيانات وهمية للإحصاءات. جميع الأعداد أتت من MySQL عبر API. كانت رسائل التحقق والنجاح والخطأ مرئية، والتنقل متجاوبًا. لم تُضف ميزات.

README يصف الأوامر والقيود والتكوين والأمان والمرحلة الحالية بدقة إجمالًا؛ التقارير القديمة لقطات تاريخية وليست ضمانًا لنفس نتائج الجولة الحالية. لكن وصف ضمان FK لا يمكن اعتماده على البيئة المحلية حتى حل QA-B01. أوامر تشغيل المصدر الحالي نجحت في العمليات المعزولة. تثبيت جديد وتهيئة قاعدة جديدة لم يُنفذا بسبب نطاق التدقيق وعدم تغيير الاعتماديات أو المخطط.

المخاطر المتبقية:

- **High للتسليم:** QA-B01؛ يحتاج سببًا وإصلاحًا مثبتًا قبل اعتماد سلامة البيانات.
- **High قبل إنتاج عام:** حساب MySQL المستخدم محليًا إداري، وTLS/proxy الفعلي غير مختبر؛ يلزم حساب محدود وHTTPS وفق README. هذا لا يعني اختبار فشل محلي جديد.
- **Medium تغطية:** suite التكامل الأصلي محجوب بسياسة عدم الحذف؛ لا اختبارات مكونات React أو lint أو نسبة coverage رقمية. البديل يغطي تدفقًا واسعًا لكنه لا يثبت حذفًا دائمًا.
