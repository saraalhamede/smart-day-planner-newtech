## 2. مدى مطابقة Bug #121438

**تطابق الشروط الظاهرة قوي؛ اختيار الفهرس الداخلي لم يُثبت.** الإصدار ووضع SQL-layer ونمط الفهرس المركب الذي يتضمن NULL تطابق البلاغ. السجلان المتأثران يحملان NULL في الأعمدة غير المرجعية ذات الصلة. دليل binlog في 6B.1 يؤكد أن الإدخالين الأصليين استعملا SQL-layer مع بقاء فحص FK مفعّلًا. [البلاغ الأصلي، وحالته Open وقت القراءة](https://bugs.mysql.com/bug.php?id=121438).

جميع فهارس tasks الحية:

| الفهرس | النوع | الأعمدة بالترتيب | أعمدة NULL |
| --- | --- | --- | --- |
| PRIMARY | unique | id | لا يوجد |
| tasks_one_in_progress | unique | user_id, in_progress_date | in_progress_date |
| tasks_user_date_time | non-unique | user_id, task_date, start_time, end_time | start_time, end_time |
| tasks_user_status_priority | non-unique | user_id, status, priority, task_date | لا يوجد |

FK الحي صحيح إلى users.id في القاعدة نفسها، والجدولان InnoDB، وuser_id نفسه NOT NULL. يوجد فهرس non-unique يبدأ بعمود FK ويتضمن أعمدة أخرى تقبل NULL؛ لكنه ليس الفهرس المرشح الوحيد. لا تكفي metadata وحدها لإثبات الفرع الداخلي أو نجاح workaround. لذلك يلزم اختبار OFF/ON مضبوط، دون إسقاط فهرس أو تغيير قاعدة مهمة نشطة واحدة.

## 4. التغيير المقترح بدقة — غير منفذ

داخل مجموعة `[mysqld]` في ملف النسخة المستهدفة:

```ini
innodb_native_foreign_keys=ON
```

للمقارنة المعزولة يبدأ الخيار OFF ثم يتغير هذا السطر وحده إلىON. إذا أُجيز تغيير الخدمة الحالية لاحقًا، يُضاف السطر إلى مجموعتها الحالية بعد backup، دون تغيير port أوdatadir أوbind أوforeign_key_checks أو.env.

المتغير Global وغير Dynamic، لذا يتطلب بدء عملية MySQL من جديد. ليس تعديل SET SESSION أوSET GLOBAL آنيًا. foreign_key_checks يبقى1. [التوثيق الرسمي للمتغير](https://dev.mysql.com/doc/refman/26.7/en/innodb-parameters.html#sysvar_innodb_native_foreign_keys).

هذا تغيير إعداد محرك، لا migration أو تعديل API. لا يصلح السجلين اليتيمين تلقائيًا؛ تبقيان دون حذف أو إعادة إسناد. ولا تُسقط الفهارس، خصوصًا tasks_one_in_progress.

## 5. الاختبار المعزول الموصى به — موافقة A مطلوبة

نستخدم binary المثبت26.7.0 نفسه، دون تثبيت حزم أو خدمة Windows جديدة:

1. إنشاء مجلد جديد وفارغ تحت `.local/phase6b2-isolated/<run-id>/` داخل المشروع. يُرفض أي مسار موجود المحتوى أو reparse point أو مسار خارج المشروع. لا نسخ أو استخدام لمجلد Data الحالي.
2. تخصيص datadir وmy.ini وlog وpid وtmpdir مستقلين داخل مسار QA، والمنفذ127.0.0.1:3307. تعطيل X في النسخة الجديدة بـ`mysqlx=0`، مع موارد محدودة مثل buffer pool128MiB وmax_connections20. لا تغيير لخدمة MySQL267 أوfirewall.
3. تهيئة الدليل الجديد فقط بواسطة `--initialize` بعد التحقق من المسار. حماية سجل bootstrap وكلمة المرور المؤقتة، وتعيين سر QA منفصل قبل تحميل أي نسخة بيانات. لا `--initialize-insecure` أو`skip-grant-tables`، ولا نشر أسرار في المخرجات.
4. تشغيل العملية مخفية بخيار`--defaults-file` أول خياراتها. حفظ UUID الجديد والتحقق أنه يختلف عن الأصلي. مطابقة إعدادات التهيئة اللازمة مثل lower_case_table_names=1 وpage size16KiB وSQL mode؛ وتثبيتها في مرحلتي المقارنة.
5. إنشاء تعريفات users/sessions/tasks المطابقة داخل قاعدة مستقلة اسمها `smart_day_planner_newtech` على3307، لأن التطبيق يتحقق من الاسم. بياناتها اصطناعية جديدة فقط؛ لا نسخ للحساب الأصلي أو حساباتQAالثلاثة أوالمهام12 إليها.
6. حساب QA محدود بالقاعدة على النسخة الجديدة، وأسرار DB وSESSION منفصلة. لا تعديل.env؛ تمرر الإعدادات في بيئة عملية QA فقط.
7. قبل كل كتابة أو تشغيل suite، guard يرفض3306 أوdatadir الأصلي أوUUID الأصلي أوإعدادًا ناقصًا قد يسقط إلى.env. حساب QA الجديد لا يملك صلاحية على3306.
8. يمكن بدء backendQA3106 وViteQA5176 بعد إعادة فحص المنافذ. يستعمل المتصفح profile اختبار مستقلًا؛ **المنافذ لا تعزل cookies على المضيف نفسه**.

[تشغيل نسخ Windows متعددة](https://dev.mysql.com/doc/refman/26.7/en/multiple-windows-command-line-servers.html)، [تعطيلX](https://dev.mysql.com/doc/refman/26.7/en/x-plugin-disabling.html)، [التهيئة](https://dev.mysql.com/doc/refman/26.7/en/data-directory-initialization.html).

لا نستخدم TEMPORARY TABLE لتجربة FK، أو مجرد schema ثانية على3306 لتجربة خيارGlobal. لا يبدأ خادم جديد علىDataالأصلي مطلقًا. يعاد التحقق من توفر الموارد والمنافذ عند التنفيذ.

تُستخدم قيم title/description/date/time/enums صحيحة حتى لا يحجب CHECK أوduplicate خطأ FK المطلوب. يثبت COUNT=0 للمالك غير الموجود داخل قاعدة QA. يسجل DATABASE وCONNECTION_ID والمتغيرات من **اتصال الإدخال نفسه**. ينفذ driver‏ ROLLBACK فيfinally عند النجاح أوالخطأ، ولا يعتمد على مواصلة SQL batch بعد1452. قد تتقدم عدادات AUTO_INCREMENT رغم rollback؛ ذلك داخل QA فقط.

إذا لم يتكرر الفشل تحتOFF نتوقف للتحقيق في اختلاف البيئة، ولا نعلن أنON أصلح حالة لم تظهر. وإذا استمر قبول مرجع خاطئ تحتON لا ننتقل إلى الخدمة الحية.

اختبارات التكامل الحالية تحذف فيfinally. تشغيلها يحتاج تصريحًا صريحًا بتنظيف **السجلات الجديدة التي تنشئها داخل instanceQA فقط**. لا توجد بيانات حقيقية في قاعدة regression، وحسابها لا يملك schemaالتحقق منbackup. إيقاف عمليةQA بعد الفحص لا يعني حذفdatadir أوالأدلة.

## 6. النسخ الاحتياطي والتحقق من الاستعادة — موافقة B مستقلة

لم يُنفذ backup أوrestore. يلزم نجاح النسخ والتحقق قبل أي تعديل للخدمة الحالية؛ التجربة الاصطناعية المعزولة لا تحتاج نقل بيانات المستخدم إليها.

1. مجلد جديد خاص تحت `.local/secure-backups/<run-id>/` بصلاحياتNTFSمحدودة. النسخة تحتوي password hashes وربما sessiontokens؛ ignore فيGit ليس حماية وصول. لا عرض أو رفع لمحتوياتها. أي نقل خارجي يحتاج تشفيرًا وطريقة حفظ مفتاح معتمدة.
2. نسخ bytes ملفmy.ini، وحفظ hash ووصف الخدمة وACL/encoding. أسماء وجهة فريدة بلا استبدال ملفات موجودة. لا نسخ لمجلدData أثناء عمل الخادم بوصفه backup صالحًا.
3. نسخة logical لكل جداول المشروع، تشمل السجلين اليتيمين دون إصلاحهما. لا `--all-databases`. ينسق توقف كتابات المشروع أثناء التحقق منmanifest، وتُمنع تغييراتDDL أثناء النسخ؛ single-transaction يعطي snapshot متسقًا لـInnoDB.
4. المثال التالي **غير منفذ**. placeholders تحل بعد موافقة وفحص المسار. --password يستدعي prompt، ولا توضع قيمة السر فيargv أوlog:

```powershell
& 'C:\Program Files\MySQL\MySQL Server 26.7\bin\mysqldump.exe' --no-defaults `
  --host=127.0.0.1 --port=3306 --user='<APPROVED_BACKUP_ACCOUNT>' --password `
  --single-transaction --quick --hex-blob --no-tablespaces --set-gtid-purged=OFF `
  --routines --events --triggers --skip-add-drop-table --skip-add-locks `
  --result-file='<VERIFIED_NEW_PRIVATE_BACKUP_FILE>' --skip-lock-tables `
  smart_day_planner_newtech
```

5. --set-gtid-purged=OFF يمنع تضمين تغييرGTID؛ المصدر الحاليGTID=ON. --skip-lock-tables يتجنب أقفالالجداول، و--result-file يتجنب مشكلات redirection فيWindows. لأنه قد يستبدل ملفًا موجودًا، يفحص المسار قبل التنفيذ. الخيارات تحقق دعمها من help المثبت، لا من تجربةbackup.
6. قبول النسخة يحتاج exit0 ومراجعة الأخطاء، وSHA-256 وmanifest للأعداد والتعاريف. ملف جزئي لا يسمى backup صالحًا ولا يُحذف تلقائيًا.
7. الاستعادة للتحقق تكون في schemaفارغة مثل `restore_verify_YYYYMMDD_HHMMSS` داخل instanceQA، بحساب مقيد بها. لا import إلى3306 أو--force أوإعادة تعريف جداول موجودة. لا خلطها بقاعدة regression الاصطناعية.
8. استعادة الحالة الأصلية قد تتطلب تعطيلFK في **جلسة الاستعادة المعزولة فقط** لإعادة السجلين اليتيمين كما كانا، ثم إثبات FK=1 مجددًا. لا يستخدم ذلك فيprobes أوالخدمة الحية. تقارن hashes وcounts والتعاريف، وتظل نسخة بيانات الاستعادة خاصة ومحتفظًا بها دونDROP أوتنظيف تلقائي.

[توثيق mysqldump26.7](https://dev.mysql.com/doc/refman/26.7/en/mysqldump.html). هذه نسخة للتطبيق وليست نسخة خادم كاملة، ولا تُعد مثبتة الصلاحية قبل تجربة الاستعادة المصرح بها.

## 7. تغيير محتمل للخدمة الحالية وخطة التراجع — موافقة C مستقلة

لا انتقال إلىC قبل نجاحA وB وإعادة inventory للخدمة. يحتاج العمل إذنًا لملفProgramData وخدمةWindows، وصلاحية مسؤولWindows إن طلبها النظام. موافقة المستخدم لا تعني توفر هذه الصلاحية؛ لا يُغيّرACL لتجاوز رفض النظام.

بعد الموافقة فقط:

1. تنسيق نافذة توقف مع مالك التطبيق وأصحاب الاتصالين غير المعرفين، وتجميد الكتابات المشروعة للمقارنة. تحديد أسلوب إيقاف/بدء backend الخاص بالمشروع؛ لا قتل لجميع عملياتnode.
2. تحديث backup وhash للإعداد. إن تغيرmy.ini عن النسخة المراجعة، تتوقف الخطة لمراجعة الفرق. إضافة سطرON واحد داخل[mysqld] مع حفظ encoding والصلاحيات؛ لا تغيير لأي خيار آخر.
3. إعادة تشغيل MySQL267 المحددة بصورة رشيقة بعد إعادة التحقق من الخدمة ومسارها؛ لا قتل تابع بـPIDقديم. اتصالاتTCP وpool وX33060 ستنقطع، وقد يلزم بدءbackend المحدد ضمن التفويض.
