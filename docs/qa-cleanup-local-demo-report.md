## 1. تحديد QA والنسخ والحذف

قُرئت تقارير 6A و6B.1 و6B.2 وأدلة `.local` القائمة. طابقت حسابات QA مع المعرّفات والأسماء وبريد `example.test` المستخدم في السيناريوهات، وطابقت صفوف المهام الاثني عشر مع بصمة الصفوف الكاملة في دليل 6B.1. لم يكفِ وجود orphan وحده لتصنيفه QA؛ ثبت أصل السجلين من دليل الإدخال والتحقيق السابق وبصمات الصفوف.

أُنشئت قبل الحذف نسخة logical كاملة لقاعدة المشروع فقط بأداة `mysqldump` المثبتة، مع `--single-transaction --quick --hex-blob --no-tablespaces --set-gtid-purged=OFF --routines --events --triggers --skip-add-drop-table --skip-add-locks --skip-lock-tables`. وصلت كلمة المرور إلى العملية عبر متغير بيئة مؤقت ولم تظهر في argv أو التقارير. لم يُكتب SQL مكشوف إلى القرص؛ شُفرت المخرجات في الذاكرة بـWindows DPAPI CurrentUser وحُفظت تحت `.local/` المتجاهل. محاولة تخصيص ACL للمجلدين لم تنتج صلاحيات owner-only في الفحص النهائي: أظهر Get-Acl صلاحيات NTFS موروثة. **الحماية المثبتة للمحتوى هي تشفير DPAPI،ولا ندعي عزل NTFS حصريًا**. لم يُغير ACL لأي مجلد قائم أو بيانات أصلية.

النسخة الأولى داخل `.local/private-backups/cleanup-6c033c81-5fa5-452b-a89c-af4f567c8c07/` وتضم `database.sql.dpapi` و`fingerprints.json.dpapi` وmanifest غير سري. كانت أعدادها4 مستخدمين و12 مهمة و3 جلسات. نجحت قراءة الملف المشفر وفك التشفير ومقارنة SHA-256 بالمخرجات الأصلية. **لم يُنفذ restore إلى MySQL**؛ تحقق البايتات لا يثبت اختبار الاستعادة الكامل. DPAPI مربوط بملف Windows الحالي؛ لا يُنقل إلى جهاز/حساب جديد بوصفه نسخة قابلة للاستعادة دون خطة مستقلة.

نُفذ الحذف بمعاملة، وشروط id/owner المحددة، وفحص البصمات قبل التنفيذ، وrollback عند أي اختلاف. حُذفت المهام أولًا ثم الجلسات المرتبطة ثم الحسابات. لم تُعطّل foreign_key_checks، ولم يُعدل أو يُحذف صف مستخدم أصلي. رفضت المراجعة التلقائية محاولة الفحص الواسع الأولى قبل التنفيذ لأنها كانت ستقرأ محتوى sessions كاملًا؛ ضُيق الفحص إلى QA وبصمات SQL وعدد الجلسات. لم يتجاوز العمل ذلك الرفض.

## 4. حفظ الأصل والعيوب المتبقية

حُسبت بصمات جميع أعمدة صفوف users/tasks داخل MySQL دون إخراج قيم المستخدم الأصلي أو password_hash. قورنت قبل التنظيف وبعده وبعد integration وبعد المتصفح، مع استبعاد معرفات QA المؤكدة فقط. النتيجة النهائية تطابق الأصل: **مستخدم واحد،0 مهام** كما كان قبل Phase6A، وتعريفات الجداول الثلاثة ثابتة بعد تجاهل عداد AUTO_INCREMENT. العدادات تتقدم طبيعيًا بكتابات الاختبار؛ لم تُصفّر أو تُعد للخلف. حفظ الجلسة الأصلية لم يتطلب قراءة محتواها؛ لم يستهدفها أي DELETE، وقد يبطلها مخزن الجلسات لاحقًا بانتهائها الطبيعي.

- **QA-B01 / High،غير محلول:** MySQL26.7.0 قبل سابقًا305 و309 بمالك غير موجود مع FKChecks=1. الأدلة السابقة ترجح Bug#121438. لم يُنفذ اختبار سببي OFF/ON أو أي إصلاح.0 orphan الآن نتيجة التنظيف فقط، وليس إثباتًا لصحة القيد مستقبلًا. نجاح API وsuite لا يختبر إنفاذ FK لهذا المسار.
- **QA-B02 / Low،غير محلول:** استعادة التركيز بعد إلغاء حوار الحذف بـEscape،وفق Phase6A. لم يُصلح أو يُعد اختبار هذا السيناريو في الجولة الحالية.
- حساب DB المحلي الإداري وحدود HTTPS والإنتاج ما زالت مخاطر موثقة؛ لا تعديل للاعتماديات أو البيئة. العرض المحلي المحدود لا يعادل تصريح نشر عام.
- النسخ محمية بـDPAPI وحساب Windows الحالي؛ اختبار استعادة مستقل غير منفذ. النسخة الأولى تحتفظ بحالة QA القديمة بما فيها orphan لأغراض الاسترجاع، ولا تُستعاد فوق الأصل تلقائيًا.

بصمة my.ini مطابقة لدليل6B.2. لم يتغير مخطط أو API أو مصدر أو اعتماديات، ولم تُنفذ أي خطوة من خطة workaround. لم تُمس المستودعات المحمية.

## 5. Git والخطوة التالية

نطاق checkpoint المقصود **خمسة ملفات توثيق فقط**: `README.md`،`docs/phase-6a-qa-report.md`،`docs/phase-6b1-fk-investigation.md`،`docs/phase-6b2-safe-fix-preparation.md`،وهذا التقرير. لا `.env` أو dump أو backup أو صور أو سكربتات QA مؤقتة في Git. يجب مراجعة الفهرس وفحص الأسرار وwhitespace قبل إنشاء commit محلي، ثم تسجيل SHA وحالة الشجرة الفعلية في التسليم؛ لا push.

المراجعة المنفذة قبل checkpoint نجحت:69 ملفًا دون أسرار محلية أو ملفات غير مقصودة،وفحوص صياغة31 ملفJS،وثبات المصدر والمخطط والاعتماديات. تطابق الفهرس مع ملفات التوثيق الخمسة المراجعة،ونجح `git diff --cached --check` وفحص قيم الأسرار داخل الفهرس. تنبيه CRLF→LF في تقرير6B.2 تطبيع نهايات أسطر Git فقط. معرف commit النهائي وحالة Git بعده يُسجلان في رسالة التسليم،ولا يُدرج المعرف داخل commit نفسه.

الخطوة التالية قرار المستخدم بشأن العيوب المتبقية أو العرض المحلي. لا متابعة تلقائية لتحقيق MySQL ولا إصلاح أو إعداد Presentation ضمن هذا التفويض. يظل قرار التسليم النهائي NOT READY من Phase6A قائمًا حتى تحقق مستقل من العيب High؛ القرار الحالي يخص إمكانية العرض المحلي الوظيفي بشفافية فقط.
